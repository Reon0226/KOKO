# KOKO 設計メモ

判断の軸は CLAUDE.md の「作り手の思い」。主役は筆跡で、字を採点しない・直さない・置き換えない。

## 1. 手書きマス（ここが KOKO の体験の中心）

| 課題 | 決めたこと | 理由 |
|---|---|---|
| 文字の確定 | タイマーで確定しない。別のマスに書き始める／‹ › ／下書きの字をタップ、の本人の操作だけで移る | ゆっくり書く人、画数の多い漢字で途中確定させない |
| 画の途中の移動 | 書いている間はマスの並びを一切作り直さない。ページ送りは › を押したときだけ（最後のマスまで書いたら › が軽く光る） | 指の下でマスが動くと、次の画が別の字に入ってしまう |
| 複数文字 | 「光っている次のマス」に直接書き始めればそのまま次の字 | 漢字ドリルと同じ感覚 |
| マスの大きさ | 画面幅と高さから自動。設定でマス2/3/4、⤢ で1マス拡大 | 小さい画面・画数の多い字 |
| 左利き | 設定で道具の並びを左右反転（送るが左） | 書く手で道具を隠さない |
| 誤タップ | ↶ は操作単位の取り消し（1画／削除／空白／改行）。⌫ の後には「↶ 戻す」を出す | 他の字を壊さず戻せる |
| 手のひら | ペンを一度使ったら、指の接触は書き込みに使わない | タブレット＋ペン |
| スクロール | マスの領域で touch-action:none と touchmove の preventDefault | 書いている間に画面が動かない |
| 長文 | 下書き欄に全文を並べ、どの字でもタップして戻れる。会話を読むときはマスをしまえる | 小画面の負担 |
| 線の記録 | 点は 0〜1 の正規化座標（小数4桁）、画ごとの経過ミリ秒、ペンなら筆圧。同じ位置に重なる点だけ間引く | 形を変えない。美文字化・平滑化はしない |
| 線の太さ | 一定の基準幅。筆圧はペンで記録された場合だけ反映 | 指の速さから太さを作るのは「補正」になるため入れていない |
| 文字の大きさ | マスの中の大きさをそのまま保つ（小さい「っ」は小さいまま届く） | その人の書き方 |

### お手本（仮案。ユーザーテストで比べる）

- 候補は「書きたい字の見本」。押しても `tokens` には何も入らない（E2E とサーバー検証の両方で確認）。
- 表示方法を設定で切替：**A. マスに薄く出す**（既定）／**B. マスの上に出すだけ**。どちらも「お手本」帯に全体を表示し、今のマスに当たる字に下線。
- お手本は空白・改行のマスを飛ばして続く。なぞりは強制しない。見本 ON/OFF あり。
- 読み取り補助が使える端末では、書いた「きもち」から「気持ち」を候補に出し、「書いた3字を消してここに書く」を**本人が押したときだけ**読みの字を消す（↶ で戻せる）。誤認識でも線は消えない。

## 2. 通信とデータ

- 認証：`POST /api/register` で端末セッション（HttpOnly・SameSite=Lax Cookie、30日、DB にはハッシュのみ）。引き継ぎコード（80bit、表示は一度だけ、ハッシュ保存、作り直し可）で再ログイン・別端末。
- 招待：本人が作るリンク `/#invite=<code>`（URL の # 以降はサーバーのログや Referer に載らない）。1回限り・7日で失効・未使用は20件まで。連絡先は扱わない。
- 1対1：`members` で参加者を管理。他人のトークは 404。
- 送信：`POST /api/conversations/:id/messages`。`(senderId, clientMessageId)` が一意。再送は 200 で同じメッセージを返す（二重にならない）。
- 受信：SSE `/api/events`。イベントは利用者ごとに連番で保存（30日）。再接続時は `Last-Event-ID` 以降を再送。500件を超えたら全体を取り直す。
- 配信状態：「送信中 → 未送信（自動で再送） → 送信済み（サーバー保存） → 届きました（相手の端末が受信）」。**既読ではありません**（既読は未決定のため入れていない）。
- 送信待ちの列：端末に保存し、1通ずつ順番に送る（順序を守る）。通信エラー・5xx・429 は指数バックオフで再送、オンライン復帰・SSE 再接続で即再送。4xx は「送れませんでした」と理由を出し、もう一度／下書きに戻す／取り消すを選べる。
- サーバー検証：参加者か、ブロック、退会、payloadVersion、最大300マス・1字80画・1画2000点・全体8万点・本文2MB、座標0〜1、時刻・筆圧の範囲、**未知のキーを拒否**（`guide` や `recognized` を入れると 422）。
- CSRF：独自ヘッダー `X-KOKO: 1` 必須＋Origin 一致。CSP は自ドメインのみ。

## 3. 安全とプライバシー

- 筆跡は個人を特定しうる情報として扱う。トークの相手以外には返さない。
- 端末に保存するもの：下書き・送信待ち・表示設定・自分と相手の名前（オフライン起動用）。**届いた筆跡は端末に保存しない**。ログアウト・全端末ログアウト・退会で端末内の KOKO データを消す。Service Worker は画面のファイルだけをキャッシュ。
- 保存方針（MVP）：メッセージは退会まで保存。退会するとその人が送った筆跡・参加・ブロック・イベントを削除し、相手の画面では「退会したユーザー」。通報は運営確認用に残る（記録は報告者・対象・理由のみ）。期限切れのセッション・イベント・招待は定期削除。
- ブロック：お互いに送れなくなる。相手に通知はしないが、相手が送ろうとすると送れないことは分かる（画面にもそう説明）。
- E2EE：未対応と明記。将来入れるなら、端末鍵（例：MLS や Signal 系プロトコル）＋サーバーは暗号文のみ保存。その場合サーバー側の座標検証はできなくなるので、サイズ上限だけをサーバーで守り、形式検証は受信側で行う設計に変える必要がある。
- 通知：開いている間だけ。本文（筆跡）は通知に出さない。

## 4. 手書き認識（読み取り補助）— 公式資料で確認したこと

- **Web Handwriting Recognition API**（developer.chrome.com/docs/web-platform/handwriting-recognition）：`navigator.createHandwritingRecognizer({languages})` → `startDrawing(hints)` → `HandwritingStroke.addPoint({x,y,t})` → `getPrediction()`。端末内で処理。Chromium 系のみ、HTTPS とトップレベルのみ。ChromeOS では英語のみと明記、日本語の記載なし。→ KOKO は機能検出し、`ja` で作れなければ「使えない」と表示する。現状、日本語では動かない前提。
- **ML Kit Digital Ink Recognition**（developers.google.com/ml-kit/vision/digital-ink-recognition）：日本語 `ja` のモデルがある。Android は `com.google.mlkit:digital-ink-recognition`（minSdk 23）、言語ごとに約20MBのモデルをダウンロードして使う。`Ink.Point.create(x, y, t)`、文脈は `RecognitionContext.preContext`（直前20文字まで）。→ ネイティブ版の第一候補。料金・利用規約・モデル配信時の通信先は、採用前に最新の規約で再確認すること（この作業では価格表・規約本文までは確認していない）。
- iOS：ML Kit の iOS 版を同じ interface（`public/js/recognizer.js` の `recognize(strokes, context)`）で包む想定。Apple の Vision の手書き日本語対応は未確認のため、ここでは採用前提にしていない。
- 認識結果は端末内の一時データ（WeakMap）で、送信データ・下書き保存には含めない。

## 5. iOS / Android に向けて

- まずこの Web 版で「話したい人と続くか」を検証。そのまま PWA としてホーム画面に追加できる（manifest・マスカブルアイコン・オフライン起動あり）。
- ネイティブ化の案：**Capacitor**（今の画面を活かしつつ、認識とプッシュ通知をネイティブで追加）を第一候補。書き心地が足りなければ、マス部分だけネイティブ描画（iOS: PencilKit ではなく自前の低遅延描画、Android: Jetpack Ink / 前方予測描画）に置き換える。
- 入力遅延：今は描きながら差分だけ Canvas に描画（getCoalescedEvents で点を取りこぼさない）。ネイティブでは 120Hz 端末の予測描画が効く。
- キーボード領域：KOKO のマスは画面の一部（OS のキーボードではない）なので、検索欄などで OS キーボードが出るときだけ高さ調整が必要（`interactive-widget=resizes-content` を指定済み）。OS 全体の手書きキーボード拡張は対象外。
- プッシュ通知：APNs / FCM。通知本文に筆跡は載せない。

## 6. 普及の検証（成功を決めつけない）

`npm run metrics` で、初回送信完了率／招待の受け入れ率／誘われた人が返事をした割合／入力時間（最初の1画〜送信、中央値・90%点）／1通の文字数／3日目以降も二人とも送っている会話の割合、を出す。筆跡や本文は読まない。

小さなテストの進め方（案）：
1. 親友・きょうだい・部活の友達など、普段から話す2人組を5〜10組。恋人に限定しない。
2. 1週間、「話したいときだけ」使ってもらう。連続利用や返信を促す通知・バッジは出さない。
3. お手本 A（マスに薄く）と B（上に出すだけ）を組ごとに切り替えて比べる。
4. 数字に加えて、「この人とは KOKO で話したい」と感じた瞬間・面倒だった瞬間を短く聞く。

## 7. 確認させてほしいこと（手書き体験を変えうるもの）

1. **お手本の既定**：A（マスに薄く）と B（上に出すだけ）のどちらを既定にするか。テスト前は A にしてある。
2. **「読み」を書いて漢字に替える流れ**：書いた読みを消すのは本人がボタンを押したときだけにした。IME のように自動で消す方が速いが、「線を失わない」に反するため入れていない。
3. **既読**：「届きました」までにしてある。既読は返信のプレッシャーになりうるので、入れるかは相談したい。
4. **活字入力**：入れていない。急ぎの連絡で困る声が出たら、「活字は小さく添える」などの案を出して相談する。
5. **アカウント**：今は引き継ぎコードのみ。小さなテストではこれで十分だが、公開前に電話番号／Apple・Google ログインのどれにするか。
